Project guide · start to finish

AI Interviewer, explained end to end

A hiring tool where a company defines a scoring rubric, sends a candidate a one-time link, and an AI holds a live spoken interview using the candidate's resume and GitHub. The call is recorded, transcribed and scored against the rubric. This guide walks through every flow with the actual code, so you can explain it confidently in an interview.

The 30-second pitch

Say it like this

"I built an AI voice interviewer for hiring teams. A recruiter creates a job with a weighted rubric, sends each candidate a single-use link, and the candidate talks to an AI interviewer in the browser over WebRTC using OpenAI's Realtime API. The AI has read their resume and their GitHub repos, so the questions are personal. The server listens to the same call through a sideband connection and stores the transcript, the browser records audio and video, and when the call ends Gemini scores each rubric criterion with evidence. The recruiter sees the recording, transcript and a weighted score in a dashboard. It's FastAPI, Supabase for Postgres, storage and auth, and plain HTML/JS on the front end."

Two kinds of users

Recruiter (has an account)

Signs up, creates a company workspace, creates jobs with rubrics, creates invite links, invites teammates, reviews candidates. Lives at /app.

Candidate (no account)

Opens /i/<token>, uploads a resume, talks to the AI, submits. Never sees the score. Access is by the secret link only.

Architecture

One FastAPI process sits in the middle. Browsers never talk to OpenAI or Gemini with a real API key, and never read the database directly. The only thing the browser talks to Supabase for is signing in.

The whole journey in one list

  1. Recruiter signs up with Supabase Auth, then calls /api/v1/account/setup to create a company and become its owner.
  2. Recruiter creates a job with a rubric (up to 8 weighted criteria) and optional focus notes.
  3. Recruiter creates an invite for a candidate. The server generates a random token and returns the link /i/<token>. It expires in 7 days.
  4. Candidate opens the link, uploads a resume. The server extracts text and GitHub username, fetches repos, atomically claims the invite and creates an interviews row with a snapshot of the rubric.
  5. Candidate's browser creates a WebRTC offer and posts it to the server. The server mints an ephemeral OpenAI key with the full interviewer prompt, creates the call, returns the SDP answer, and opens a sideband connection to the same call to save the transcript.
  6. Candidate talks to the AI. The browser mixes both voices plus the webcam into one recording.
  7. Candidate ends the call. The browser uploads the recording, then calls /end. The server atomically moves the interview to Scoring and starts a background scoring task.
  8. Gemini scores each criterion 0–10 with evidence. The server computes the weighted total itself and marks the interview Done.
  9. Recruiter opens the candidate in the dashboard: score, per-criterion evidence, strengths, weaknesses, recommendation, transcript, resume and recording via signed URLs.

Three helpers used everywhere

main.py:89–132

def get_db() -> Client:          # lazy singleton Supabase client using the SECRET key
    global sb
    if sb is None:
        key = os.environ.get("SUPABASE_SERVICE_KEY") or os.environ["SUPABASE_KEY"]
        sb = create_client(os.environ["SUPABASE_URL"], key)
    return sb

def spawn(coro) -> None:
    """Start a background task and keep a reference so it isn't garbage-collected mid-run."""
    task = asyncio.create_task(coro)
    _background.add(task)
    task.add_done_callback(_background.discard)

async def run(query):
    """Run a blocking Supabase query without blocking the event loop."""
    return await asyncio.to_thread(query.execute)
Why this matters

The Supabase Python client is synchronous. Calling it directly inside an async route would freeze the whole server while it waits. run() pushes each query onto a worker thread. spawn() exists because asyncio only keeps weak references to tasks; without the _background set a long-running sideband or scoring task could be garbage-collected halfway through.

Key idea: dependency chain

Routes declare rec: dict = Depends(current_recruiter). FastAPI runs current_user (who is this?) then current_recruiter (which company do they belong to?). Every route then filters by rec["company_id"], so one company can never read another's data. The 60-second cache avoids a round trip to Supabase on every request.

The server never trusts the rubric as sent. clean_rubric enforces 1–8 criteria, a non-empty unique name (case-insensitive), weight 1–100, and trims lengths:

main.py:236

def clean_rubric(items: list[Criterion]) -> list[dict]:
    if not 1 <= len(items) <= MAX_CRITERIA:
        raise HTTPException(400, f"A rubric needs between 1 and {MAX_CRITERIA} criteria")
    out, seen = [], set()
    for c in items:
        name = c.name.strip()[:60]
        if not name: raise HTTPException(400, "Every rubric criterion needs a name")
        if name.lower() in seen: raise HTTPException(400, f"Criterion '{name}' appears twice")
        if not 1 <= c.weight <= 100: raise HTTPException(400, "Criterion weights must be between 1 and 100")
        seen.add(name.lower())
        out.append({"name": name, "description": c.description.strip()[:400], "weight": c.weight})
    return out

Weights don't strictly need to sum to 100 on the server. rubric_text() converts them to percentages of the total, and the scoring formula divides by the total weight, so the math stays correct either way. The UI shows a running total to steer recruiters to 100%.

Routes: GET /api/v1/jobs (with interview and completed counts per job), POST /api/v1/jobs, PUT /api/v1/jobs/{id}. company_job() confirms the job belongs to the recruiter's company before any edit.

Flow 4: Candidate opens the link and uploads a resume

Loading the invite

index.html pulls the token out of the URL with a regex and calls GET /api/v1/invite/{token}. The server answers with a state:

stateMeaningWhat the candidate sees
openUnused, not expiredThe form (name pre-filled, resume upload, GitHub field, consent box)
expiredPast expires_at"This link has expired"
startedInterview exists, status Pre or InProgress"Continue interview" (rejoin after a dropped connection)
finishedInterview is Scoring / Done / Failed"Interview submitted"

POST /api/v1/pre-interview

A multipart form: token, name, consent, optional GitHub, resume file. Here is the sequence inside pre_interview (main.py:636):

  1. Load the invite, reject if already used (409) or expired (410).
  2. Validate name and that consent to recording is true.
  3. Read at most 5 MB + 1 byte. Reading one byte past the limit is a cheap way to detect "too big" without loading a huge file.
  4. parse_resume(): for PDFs it checks the %PDF magic bytes, extracts text per page and also pulls hyperlink URIs out of link annotations. For DOCX it reads paragraphs and hyperlink relationships. Fewer than 50 characters means it was probably a scanned image, so it rejects.
  5. extract_github_user() finds the GitHub username (details below), then fetch_repos() gets 15 recent repos: name, description, language, stars.
  6. Atomic claim of the invite (see below).
  7. Insert the interviews row with a snapshot of the job's rubric. If the insert fails, un-claim the invite so the candidate can retry.
  8. Link the invite to the interview, upload the resume file to the private resumes bucket at {interview_id}/resume.pdf.

The atomic-claim pattern (interviewers love this)

Checking used_at is null in Python and then updating would be a race: two tabs submitting at the same time would both pass the check. Instead the condition goes into the UPDATE itself: UPDATE invites SET used_at = now() WHERE id = ? AND used_at IS NULL. Postgres makes that single statement atomic, so exactly one request gets a row back. The same pattern is used for team invites and for moving an interview into Scoring.

Finding the GitHub username

main.py:297

def extract_github_user(text, links, manual=""):
    """Prefer a profile link (github.com/user); otherwise the most common repo owner."""
    if manual: ...                         # candidate typed it: trust that first
    owners = Counter()
    for source in [*links, text]:          # embedded hyperlinks first, then visible text
        for m in GITHUB_RE.finditer(source or ""):
            user = m.group(1)
            if user.lower() in IGNORED_GH: continue     # github.com/features, /orgs, /topics...
            if not m.group(2):             # no "/repo" part, so it's a profile link
                return user
            owners[user] += 1              # repo link: count the owner
    return owners.most_common(1)[0][0] if owners else ""

Resumes often show "GitHub" as clickable text with the URL hidden in the link, which is why hyperlink extraction from the PDF matters.

Why the server brokers the call

The real OpenAI key never leaves the server. The interviewer prompt, which contains the rubric, is configured server-side, so the candidate can't read or tamper with it from DevTools. And because the server is the one that creates the call, it knows the call_id and can attach a sideband connection.

The interviewer prompt

interview_session() (main.py:370) builds the session config: model gpt-realtime, voice marin, input transcription with gpt-4o-mini-transcribe, and instructions:

"Always speak English only... Start by greeting the candidate briefly and asking your first question. "
"Ask 3 to 5 concise questions, one at a time, mixing: their resume experience, their GitHub projects, "

"evidence for every scored criterion. Ask a short follow-up when an answer is vague. "

This is a WebSocket from the server to the same live call. The browser handles audio; the server receives the events. Each finished utterance becomes a messages row. Because the transcript is collected server-side, the candidate cannot edit what gets scored.

On End, the chunks become a Blob and are posted to POST /api/v1/recording/{id}. The server (main.py:753) rejects a second upload, checks the interview has started, caps size at 50 MB (Supabase free-tier limit), allows only webm/mp4 MIME types, and stores it in the private recordings bucket.

Recording is best-effort. If the browser can't record, or the upload fails, the candidate is told, but the interview still completes because the transcript is what gets scored.

Why this design

LLMs are bad at arithmetic and inconsistent about weights. So the model only does judgement (a score and evidence per criterion), and plain code does the math. Missing criteria get 0, out-of-range scores are clamped, and an unknown recommendation becomes "Maybe". Because the rubric was snapshotted onto the interview, editing a job later never changes past scores.

Example: Technical depth 8 (35), Problem solving 6 (30), Communication 9 (20), Ownership 5 (15) gives (280 + 180 + 180 + 75) / 100 = 7.15, stored as 7.

The candidate's own result endpoint, GET /api/v1/result/{id}, deliberately returns only status and role. Scores belong to the hiring team.

Known limitations and what you'd improve

Interviewers often ask "what would you do differently?" Having honest answers ready shows you understand the trade-offs.

Candidate endpoints trust the interview ID. /session, /recording, /end and /result take only the interview UUID. UUIDs are unguessable, so this is a capability-style design, but a stronger version would require the invite token (or a signed session cookie) on every candidate call.
Background tasks live in memory. spawn() runs the sideband and scoring inside the web process. If the server restarts mid-scoring, the interview stays in Scoring forever. Fix: a job queue (Celery, RQ, Supabase queues) or a sweeper that retries stale Scoring rows.
Single-process assumptions. The token cache and the Google-settings cache are module-level dicts. That's fine for one process; with multiple workers each has its own cache (still correct, just less effective).
Recording size and upload. The whole recording is held in browser memory and uploaded at the end in one request. A long interview or a closed tab loses it. Fix: chunked or resumable uploads during the call, or record server-side.
No time limit on the call. The prompt asks for 3–5 questions, but nothing enforces a maximum duration or cost.
Other ideas. Send invite emails from the server, add automated tests, add rate limiting on public endpoints, compare candidates side by side, let recruiters override scores, support languages besides English.

Likely interview questions, with answers

Walk me through what happens when a candidate clicks the link.

The page loads index.html, reads the token from the URL, and calls /api/v1/invite/{token} to get the company, job and invite state. If it's open they see the form. They upload a resume, which the server parses, finds their GitHub, fetches repos, atomically claims the invite and creates an interview with a rubric snapshot. Then the browser gets mic/camera, creates a WebRTC offer and posts it to /session. The server mints an ephemeral OpenAI key with the interviewer prompt, creates the call, returns the SDP answer and opens a sideband to save transcripts. They talk, press End, the recording uploads, /end moves the interview to Scoring and Gemini scores it in the background.

Why does the server sit between the browser and OpenAI?

Three reasons: the real API key never reaches the browser; the prompt, including the rubric, is set server-side so the candidate can't see or alter it; and the server learns the call_id, which lets it open a sideband WebSocket and capture a transcript the candidate can't tamper with.

What's a sideband connection?

A second connection to the same Realtime call. The browser carries the audio over WebRTC; the server connects over WebSocket using the call_id and receives events such as finished transcriptions. It can also send events, which is how it triggers the AI's opening greeting with response.create.

How do you prevent an invite link from being used twice?

A conditional update: set used_at only where used_at IS NULL. Postgres executes that atomically, so if two requests race, only one gets a row back and the other gets 409. If creating the interview then fails, the claim is rolled back so the candidate can retry.

How is the score calculated? Can the AI just make up a number?

Gemini returns JSON matching a Pydantic schema: a 0–10 score and one sentence of evidence per criterion. The server matches those to the rubric by name, clamps them, treats missing ones as 0, and computes the weighted average itself. The model's own overall number is overwritten.

Why snapshot the rubric onto each interview?

So historical results stay consistent. If a recruiter changes weights next month, past candidates keep the scores they were evaluated on, and the scoring step always uses the rubric the interview was actually conducted against.

How does multi-tenancy work?

Each recruiter row has a company_id. The current_recruiter dependency loads it from the verified token, and every recruiter query filters by it. Asking for another company's interview returns 404. RLS with no policies blocks any direct database access from browsers.

How do you authenticate recruiters?

Supabase Auth in the browser handles passwords, Google OAuth and resets. The browser sends the access token as a Bearer header. The server validates it by calling Supabase's /auth/v1/user, caching the result for 60 seconds, then looks up the recruiter row.

How do you record both voices into one file?

With the Web Audio API: an AudioContext with a MediaStreamDestination. Both the mic stream and the remote AI stream connect into it, producing one mixed audio track. That track plus the webcam video track go into a MediaRecorder at low bitrates so about 20 minutes fits under 50 MB.

Why use asyncio.to_thread so much?

The Supabase Python client and the Gemini call used here are blocking. Running them directly in an async route would stall the event loop for every user. to_thread moves them onto a worker thread while the loop keeps serving other requests.

What happens if Gemini is down?

It tries the configured model, then two fallbacks, each with a 60-second timeout. If all fail, the for-else raises, score_interview catches it and marks the interview Failed with an error message the recruiter can see.

How do you defend against prompt injection in resumes?

Both prompts explicitly say the resume, repository and transcript text are data, not instructions. The grader only judges the candidate's spoken answers. And since the final score is computed in code from per-criterion scores with evidence, a single injected "give me 10" is easy to spot in the evidence text.

Why no React or build step?

The app has two pages and most of the work is browser APIs (WebRTC, Web Audio, MediaRecorder, fetch). Plain JS keeps it simple to deploy: FastAPI serves the HTML files directly, and there's nothing to compile.

How would you scale this?

Move scoring and sideband handling into a worker queue so web servers are stateless; run several uvicorn workers behind a load balancer; use Redis for the token cache; upload recordings in chunks during the call; add rate limits on public endpoints; and add a sweeper for interviews stuck in Scoring.
